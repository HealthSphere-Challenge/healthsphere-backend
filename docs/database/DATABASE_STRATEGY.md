# PostgreSQL and migration strategy

Approved stack: Python 3.13 managed with `uv`; FastAPI → synchronous SQLAlchemy 2 → psycopg 3 → PostgreSQL; Alembic owns schema history. No pgAdmin application dependency. HS-002 creates no database, table, model, migration, or dependency manifest.

## Configuration and lifecycle

`DATABASE_URL` is required local runtime configuration; `.env.example` contains an empty template, not credentials. Use an ignored local `.env` or deployed secret configuration. Never hardcode credentials or print connection strings. Local PostgreSQL installation/readiness is unverified. Development roles/database provisioning will be documented during HS-004; migrations, not ad-hoc table creation, manage application schema.

`TEST_DATABASE_URL` must point to a separately provisioned test database. Tests fail closed if missing or equivalent to the development database after normalization, even when credentials differ. Compare host/port/database identity; explicit test naming/provisioning safeguards accompany any destructive cleanup. Do not silently fall back to `DATABASE_URL`. PostgreSQL integration tests must not use SQLite as evidence of PostgreSQL behavior.

Services own the logical transaction boundary. Repositories share its scoped synchronous session; request sessions close on success/failure and roll back errors. Route style must respect synchronous database execution rather than mix blocking calls into async handlers. Pool size and timeouts follow the selected runtime/deployment plan.

## Future schema rules

One account maps to one profile, enforced by database constraints as well as services. Application primary keys use UUIDv4 stored as PostgreSQL `uuid`. Instants use `timestamptz` normalized to UTC; dates such as date of birth use `date`. Profile completeness and omitted/null/empty distinctions must survive persistence. Measurements store canonical units, observation time, ingestion time and ownership; weight measurements are authoritative and BMI is derived. Assessment records need model provenance and input snapshot semantics. Exact columns, indexes and migration design remain **PENDING HS-006/008/012-BE**. Conversation retention is 30 days for the prototype; deletion mechanics and backup policy remain **PENDING HS-013/016**.

Every schema change includes SQLAlchemy mapping, Pydantic impact review, Alembic migration, service/repository impact, integration validation and compatibility/rollback consideration. Review autogenerated migrations; never accept unreviewed drops, default backfills or constraints. CI checks a single intended migration head, fresh upgrade, and compatible upgrade from the prior schema where relevant. Validate downgrades when supported; document irreversible data changes and restore strategy instead of promising impossible rollback.

Runtime startup must not create permanent application tables with `create_all`. No direct production table edits as the ongoing workflow. File uploads remain deferred and, when approved, bytes belong in secured file/object storage, with metadata in PostgreSQL.
